# 泰拉时间线 · 设计说明

《明日方舟》统一事件时间表。本文回答四件事：**怎么用（交互）**、**数据长什么样（结构）**、
**谁能改什么（权限）**、**AI 怎么接入以及怎么保证多人编辑下时间线不崩（一致性与冲突）**。

---

## 0. 出发点是三个现实约束

设计中的所有取舍都来自这三个约束，先讲清楚，后面的决策才不是凭空来的。

| 约束 | 表现 | 对设计的影响 |
| --- | --- | --- |
| **泰拉历不是可用历法** | 「1096年12月23日」「1097年冬」「1098年」「纪元前（年表未载）」并存，还有大量相对时间 | 时间必须以**区间 + 精度 + 可信度**建模，不能落成 datetime |
| **内容天然不可信** | 官方明写、设定集推断、社区考据混杂，彼此矛盾 | 每条时间都带 confidence，并区分「已确证 / 推断 / 存疑」 |
| **协作方是考据者，不是运维** | 他们会改错、会重复录、会中途关页面 | 不能靠硬锁与互斥；要靠可见性、可回滚与收敛式巡检 |

## 1. 交互设计

### 1.1 信息架构

```
/                     时间线（公开可读）
  ├─ 左侧筛选栏       时间轴 / 纪元 / 出处 / 阵营人物 / 标签 / 状态
  ├─ 中部时间线       按纪元分组的条目流 + 顶部时间轴概览
  └─ 右侧抽屉         条目的查看 / 编辑 / 标注 / 版本
/sources              出处与语料库（AI 梳理的输入源）
/sources/{slug}       单个出处：原文录入 + 触发梳理 + 该出处条目
/proposals            AI 审核台（提案队列 + 梳理表单）
/anomalies            一致性收件箱（巡检产出的异常）
/login                登录
```

四页的划分对应四种角色动作：**读**（时间线）、**写**（抽屉）、**灌语料**（出处）、**裁决**（审核台 / 收件箱）。
刻意没有把 AI 审核台做成时间线的一个模式 —— 它是「AI 内容进入时间线前必须经过的关卡」，独立成页才有仪式感与责任感。

### 1.2 时间线页

- **纪元色带分组**：条目按所属纪元成组，组头显示纪元名、区间与条数。纪元的颜色贯通筛选器、缩放条与卡片，形成空间记忆。
- **缩放条（canvas）**：把全站条目按年聚合成直方图，纪元以色带铺底。**拖选一个区间即等于一次时间筛选**，是「先看分布、再钻细节」的主路径。
- **「时间未定」独立泳道**：未定位时间的条目统一排在最后，不插入时间序列。原因是把未知混进有序列表会污染排序语义 —— 用户会误以为它「发生在 0 年」。
- **条目标记语言**：
  - 左侧时间轴节点颜色 = 时间可信度（绿=已确证 / 黄=推断 / 红=存疑）
  - 卡片左边框 = 状态异常（红=一致性告警 / 黄=冻结）
  - 徽章区直接展示精度、可信度、告警数、锁定态
  - 纪年原文永远以等宽字体原样显示，**不做任何「友好化」改写**
- **详情抽屉四页签**：详情（含出处引文）/ 编辑 / 标注 / 版本。信息与操作分离，读的时候不会被表单干扰。
- **编辑即声明基线**：编辑页顶部明确写出「本条目当前版本 v12，保存时会携带该版本号」，让并发规则对用户可见，而不是失败后才解释。
- **冲突面板**：不做「保存失败，请刷新」这种丢输入的处理，而是把字段级三方 diff（基线 / 对方 / 我方）铺开，未打架的改动自动并入，只让用户裁决真正打架的那几个字段。
- **标注入口对所有访客开放**：纠错的门槛必须低于改正文的门槛，否则时间线的纠错回路会断。编辑页不可用时，会提示改走标注通道。

### 1.3 AI 审核台

三段式：**触发区**（选出处 / 粘原文 / 定目标纪元）→ **队列区**（状态计数 + 批量采纳）→ **提案卡**（折叠展开）。

每张提案卡展开后必须能回答「我凭什么信它」，因此固定包含：

1. 阻断与待补正问题（硬闸门 / 软闸门分开呈现）
2. 摘要
3. **出处核验**：逐条引文标出「已在原文定位 ✓ / 原文中找不到 ✗」与字符偏移
4. **校验明细**：结构、时间可解析、出处定位命中数
5. **一致性预检**：时代错位 / 疑似重复 / 锚点失效
6. 关联人物、阵营、建议标签
7. 模型原始返回（可展开）
8. 操作：采纳为新建 / 合并进既有 / 驳回（必填理由）

### 1.4 视觉与可用性

- 基调：终端 / 档案柜。深色底 + 青蓝主色（罗德岛）+ 琥珀警示色，等宽字体承载一切纪年与版本号。
- 无构建步骤：容器内没有 Node，因此手写 CSS 与原生 JS，由 `<body data-page>` 分派页面逻辑。
- 空状态都给出下一步动作（空时间线 → 引导去 AI 梳理；空提案区 → 引导粘贴语料）。
- Esc 关闭抽屉与冲突面板；抽屉打开时自动获取编辑租约。

## 2. 数据结构

### 2.1 时间模型（最关键的一张表）

时间存为**闭区间** `[start_index, end_index]` 加两个枚举，而不是单个时间戳：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `date_display` | string | **原始纪年文本**，展示层只认它 |
| `start_index` / `end_index` | integer | TerraDate 网格索引，可比较、可聚合 |
| `date_precision` | enum | day / month / season / year / range / relative / unknown |
| `date_confidence` | enum | confirmed / inferred / disputed / unknown |

网格索引是单调递增的整数，与公历闰年、月末无关：

```
index = year * 372 + (month - 1) * 31 + (day - 1)
```

**为什么不用 Carbon。** 把「1097年冬」存成 `1097-12-01` 就是伪造精度：它会让排序看起来更整齐，
但在「1098 年 1 月是否属于 1097 年冬」这类判断上直接出错，而且用户无法察觉。
用整数网格 + 区间语义，精度不足只体现为「区间更宽」，语义始终正确：

```
day     → [d, d]
month   → [月初, 月末]
season  → 春=3–5月  夏=6–8月  秋=9–11月  冬=12月–次年2月（跨年，月份允许 > 12）
year    → [1月1日, 12月31日]
range   → 显式区间
relative→ 索引置哨兵 0，等锚点事件确定后再回填
unknown → 索引置哨兵 0，归入「时间未定」泳道
```

**区间查询用重叠而不是包含**：`end_index >= from AND start_index <= to`。
这是「1097年冬」能被「1098年1月」命中的唯一原因，也是最容易被写成 bug 的地方（有测试专门守着）。

**排序是全序且稳定的**：

```sql
ORDER BY (date_precision = 'unknown') ASC,  -- 未定位排最后
         start_index ASC, sort_seq ASC, id ASC
```

第一顺位用 CASE 把未定位条目踢到最后：若只按 `start_index` 排，它们（索引 0）会插在「纪元前」（负索引）与「1038 年」之间。

**展示层永远回落到 `date_display`**，绝不从索引反推格式化 —— 一旦反推，就又会伪造精度。

### 2.2 字典层

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `eras` | name, slug, date_label, start_index, end_index, color | 时期切分。区间用于「时代错位」巡检 |
| `factions` | name, parent_id, color | 支持层级；筛选按母阵营时向下包含子阵营 |
| `characters` | name, codename, faction_id | 人物 |
| `sources` | name, type, code, chapter, release_order, **raw_text** | 出处。`raw_text` 是溯源链的根 |
| `tags` | name, color | 人工自由标注维度 |

`sources.raw_text` 是整个机制的地基：AI 抽取出的每条引文都要回到这段文本做字符偏移定位，
人工也能顺着偏移点回原文核对。因此把原文录进系统本身就是一项有价值的工作。

### 2.3 核心表 `events`

按用途分四组字段：

```
内容      title / summary / details / location
时间      date_display / start_index / end_index / date_precision / date_confidence / era_id / sort_seq
结构      parent_event_id（归纳） / caused_by_event_id（因果）
协作      status / version / is_locked / created_by / updated_by / verified_* / deleted_at
```

`parent_event_id` 与 `caused_by_event_id` 不是装饰：它们是「因果倒置」「子早于父」两类巡检的判据，
没有这两个字段，语义一致性问题就只能靠人眼发现。

### 2.4 关系层与协作层

关系表（`event_source` / `event_character` / `event_faction` / `event_tag`）都是**关系表 + 元数据**，
而不是 JSON 列 —— 只有这样才能按维度建索引检索（「按阵营筛选」是最常用的入口之一）。

| 表 | 作用 |
| --- | --- |
| `event_revisions` | 全量版本快照。三重用途：审计、三方合并的 base、回滚 |
| `annotations` | 标注 / 纠错建议，访客可用 |
| `event_locks` | 编辑租约（软锁），不阻塞但可见，到期自动回收 |
| `ai_proposals` | **AI 产出暂存区**，AI 永不直接写 events |
| `timeline_anomalies` | 一致性异常收件箱，`fingerprint` 唯一索引防重复告警 |
| `source_user` | 出处归属，用于限制编辑者的改动范围 |

`event_revisions` 上有 `unique(event_id, version)`。这个约束不是装饰 —— 它保证了「一个版本号只对应一次写入」，
任何试图在同一版本写两条记录的代码都会立刻失败（开发期就撞到过，见 §5.3）。

## 3. 编辑权限

### 3.1 角色与能力矩阵

| 能力 | viewer | editor | reviewer | admin |
| --- | :-: | :-: | :-: | :-: |
| 浏览时间线 / 检索筛选 | ✔ | ✔ | ✔ | ✔ |
| 提交标注（评论、纠错、存疑） | ✔ | ✔ | ✔ | ✔ |
| 新增 / 修改 / 删除条目 | — | ✔ | ✔ | ✔ |
| 发起 AI 梳理（产出提案） | — | ✔ | ✔ | ✔ |
| 查看审核台 | — | ✔ | ✔ | ✔ |
| **采纳 / 合并 / 驳回 AI 提案** | — | — | ✔ | ✔ |
| 标记「已校验」、裁定争议 / 废弃 | — | — | ✔ | ✔ |
| 锁定 / 解锁条目 | — | — | ✔ | ✔ |
| 处置一致性异常、强制接管编辑租约 | — | — | ✔ | ✔ |
| 回滚历史版本、恢复已删条目 | — | — | ✔ | ✔ |
| 管理用户 / 字典 | — | — | — | ✔ |

三条刻意设计：

1. **读永远开放**。考据项目的价值来自可被引用，不能先登录再看。
2. **看提案 ≠ 放行提案**。editor 可以看提案、可以跑梳理（产出必然停在待审），但只有 reviewer 能把 AI 内容写进时间线。
3. **标注对所有人开放**，包括未登录访客（`user_id` 记 null 以示区别）。

### 3.2 权限的三个叠加约束

即便角色够，还要同时满足：

- **条目状态**：`disputed` / `deprecated` 的条目正文冻结，editor 只能提交标注建议；reviewer 可直接改。
- **条目锁定**：reviewer 锁定后，editor 连改都改不了（常用于争议条目的集中讨论期）。
- **出处归属**：`users.strict_source_scope` 开启时，editor 只能改自己负责的出处（`source_user`）相关条目。
  未归属任何出处的条目对所有 editor 开放，避免出现「无主的条目谁也改不了」。

### 3.3 权限判定的默认方向

`User` 模型上显式声明了 `$attributes = ['role' => 'viewer', 'strict_source_scope' => true]`，
并提供 `enforcesSourceScope()` 把 null 当 `true`。

原因是实测踩到的：`User::create([...])` 不会把未提交的列补进属性数组，
于是 `$user->strict_source_scope` 会读到 null，而 `null` 是 falsy —— 出处范围限制被静默绕过。
**权限判断的默认方向必须是更严，而不是更松**，这一条写进了模型注释与测试。

## 4. AI 补全：触发与校验

### 4.1 铁律

> **AI 的任何输出都只能落在 `ai_proposals`。`events` 表只能由人工在审核台放行后写入。**

原因：幻觉在产品层的表现不是报错，而是时间线上多出一条「看起来完全合理」的假事件，
比缺失更难被发现。所以宁可牺牲自动化程度，也要保住这一道人工关卡。

### 4.2 触发方式

| 方式 | 入口 | 说明 |
| --- | --- | --- |
| 出处补全 | 出处详情页「开始梳理」 | 用 `sources.raw_text` 整段作为输入，最常用 |
| 即席梳理 | 审核台粘贴文本 | 临时片段，可选回写到出处（便于后续复现与定位） |
| 报告式补全 | 审核台选择出处 | 不粘文本，直接跑该出处已存语料 |
| 自动触发 | 新建出处且已填 `raw_text` | 走队列，避免长请求阻塞（预留 `SynthesizeEventsJob` 位置） |

### 4.3 驱动抽象与降级

```
AiDriver (interface)
  ├─ HeuristicAiDriver      纯规则离线抽取，零依赖零成本
  └─ OpenAiCompatibleDriver 任意兼容 /chat/completions 的服务
```

`heuristic` 驱动的定位不是「假装是 AI」：它按纪年表述切出候选窗口，既能在没有密钥时兜底，
也能作为 LLM 的前置过滤器把 token 消耗砍掉一个数量级，还能作为判定「模型出问题还是语料出问题」的基线。

配置了 `openai-compatible` 但**没填密钥时会静默降级到 heuristic 而不是抛异常** ——
AI 梳理是增强功能，它挂掉不该让整个站点不可用。

提示词里三条硬要求都是为了配合下游校验：强制 JSON、强制提供**逐字原文引用**、注入既有条目清单以抑制重复。

### 4.4 四层校验

任何一层不过，都进不了 `events` 表。

| 层 | 内容 | 不通过的后果 |
| --- | --- | --- |
| **L1 结构** | 必填字段非空、`confidence` 落在 0–100、数组字段结构正确 | 直接丢弃，不生成提案 |
| **L2 时间可解析** | `date_display` 必须能被解析出网格索引 | 记为「需补正」，禁止直接入库 |
| **L3 出处可定位** | 每条 `evidence.quote` 必须在 `raw_text` 中定位成功（归一化子串匹配，容忍空白与标点差异，**不容忍改写**），并回填字符偏移 | 记为 `unverified`，**硬闸门** |
| **L4 一致性** | 只读预检：时代错位、疑似重复、相对时间锚点失效 | 阻断级问题禁止直接入库 |

外加**批次内去重**与**与既有条目去重**（2-gram Jaccard + 包含关系提权），重复项落为 `duplicate` 并挂上 `duplicate_of_event_id`。

校验结论全部写进 `ai_proposals.validation` 一并持久化，因此审核人可以离线复现「当时为什么被判为有问题」。

### 4.5 闸门的两级设计

初版把所有问题放进一个 `blockingIssues()`，结果发现一个漏洞：**审核人只要传任意 `overrides` 就能绕过出处校验**，
顺手改个标题就把一条毫无出处的幻觉内容放进了时间线。修正为两级：

- **硬闸门（hardIssues）**：只有「缺少可定位的原文引用」一条。
  不可被 `overrides` 绕过，必须显式传 `acknowledge_missing_evidence = true` 才能放行，
  且审核记录里会留下「⚠️ 已确认该提案无原文出处支撑」的免责痕迹。
- **软闸门（softIssues）**：时间不可解析、一致性阻断。允许审核人**补正字段后**放行，
  但「什么都不改直接放行」依然被拒。

### 4.6 审核动作与反馈闭环

- **采纳为新建**：生成条目，状态固定为 `needs_review`（还需人工再点一次「标记已校验」），
  revision 的 `origin = ai`、`user_id = 审核人` —— 「谁为这条 AI 内容负责」永远有答案。
- **合并进既有条目**：不丢信息。提案里的出处引文与关联人物会**追加**到目标条目，
  并留一条 annotation 说明来源。
- **驳回**：理由必填，写入 `review_note`，作为 prompt 调优的反馈数据集。

采纳后还会把该条目的一致性异常 `ai_proposal_id` 回填，方便日后复盘「哪一批 AI 产出更容易出问题」。

## 5. 多人编辑下的一致性与冲突处理

冲突分成三个层次，**用三种不同的机制分别解决** —— 试图用一个机制包打天下是这类系统最常见的失败。

### 5.1 结构层：时间线不会被「拆断」

**做法：排序是派生量，不是存储量。**

条目的顺序由 `(start_index, sort_seq, id)` 在查询时计算得出，表里没有 `prev_id` / `next_id` 这类链表字段。
因此：

- 并发插入两个「1097 年 3 月」的条目，不需要任何协调，两者的相对顺序由 `id` 决定，都是合法结果；
- 分页是稳定的 —— 新增条目只会让后续页整体后移，不会出现漏条或重条；
- 「移动条目到另一个时间点」退化成一次字段更新，不必维护邻居指针。

这是整个一致性设计里最省事的一层：**把顺序当作查询结果而不是数据，就没有一致性问题。**

### 5.2 字段层：乐观锁 + 三方合并

**写入用 compare-and-swap，不是「先读后写」。**

每次写入携带客户端读到的 `version`，服务端执行条件更新：

```sql
UPDATE events SET ..., version = ? + 1
WHERE id = ? AND version = ?
```

命中 0 行即说明有人抢先写入 → 抛 `EditConflictException`。这是数据库层面原子的，
不依赖应用层锁，也不受进程数影响。

**冲突时不报错，而是做字段级三方比对。** 拿客户端声明的基线版本对应的 revision 快照作为 `base`，
与 `theirs`（当前值）和 `mine`（本次提交）逐字段比较：

| 情况 | 处理 |
| --- | --- |
| 只有对方改了 | 保留对方，记入 `theirsOnly`，**自动并入** |
| 只有我方改了 | 采用我方，记入 `mineOnly` |
| 双方都改、值相同 | 不算冲突（殊途同归） |
| 双方都改、值不同 | **字段级冲突**，交用户裁决 |
| 本次没提交该字段 | 对方改了就用对方的 |

关系字段（出处 / 人物 / 阵营 / 标签）也参与比对。初版只比标量属性，会出现
「两个人同时改了出处却没有任何提示」的静默覆盖，已修正为整份快照比对。

**基线不可用时的保守策略。** 若客户端声明的版本快照已被裁剪（拿不到 `base`），
不采用「以对方为基线」的乐观假设（那等于把客户端提交的内容一律当成己方改动、静默覆盖对方），
而是**把所有不一致都判为冲突**交给用户裁决。宁可多问一次，也不能悄悄丢掉别人已经确认过的内容。

**冲突裁决的回写**走 `/events/{id}/resolve-conflict`：客户端给出逐字段裁决（`mine` / `theirs` / 自定义值），
服务端以**最新版本**为基线拼装后重新 CAS 写入，因此不会二次冲突（除非这几秒内又有人写入，那会再返回一次 409 并刷新面板）。

**格式校验规则单点定义。** 创建与更新共用同一个 trait 的规则集，避免两处漂移 ——
校验规则漂移是协作系统里最隐蔽的 bug 来源。

### 5.3 软锁：为什么不做硬锁

编辑条目时会获取一个 **5 分钟的编辑租约**（`event_locks`，60 秒续租，到期自动回收）。

它是**软锁**：**不阻止他人编辑**，只把「谁正在编辑什么」公开出去，让冲突从「信息不对称导致的重复劳动」
变成「可预期的合并」。理由：

- 硬锁会产生僵尸锁（用户直接关标签页），把条目永久锁死，比偶尔的冲突严重得多；
- 真正的数据安全已经由乐观锁保证 —— 即使软锁被绕过，也不会丢更新。

租约被他人持有时，接口返回 409 + `locked_by_other`，前端提示但仍允许提交（会走冲突合并）。
审核员可以强制接管，保留人工兜底。

### 5.4 语义层：收敛式巡检

上面两层解决的都是「同一秒的写入竞争」。但绝大多数不一致其实是语义层的：
**A 把事件定在 1097 年，B 把它的起因定在 1099 年 —— 两个人都没写错格式，拼起来是错的。**
这类问题无法在写入瞬间判定，只能用规则持续收敛。

`TimelineConsistencyChecker` 的检查项：

| 类型 | 判据 | 级别 |
| --- | --- | --- |
| 因果倒置 | `event.start_index < caused_by.start_index` | 阻断 |
| 子早于父 | `event.start_index < parent.start_index` | 阻断 |
| 锚点失效 | 精度为 relative 且索引未解析 | 阻断 |
| 时代错位 | 条目索引落在所属纪元区间之外 | 警告 |
| 出处矛盾 | 出处引文中的年份与条目年份相差超过容差 | 警告 |
| 疑似重复 | 标题相似度 ≥ 阈值且时间区间重叠 | 警告 |
| 单日过载 | 同一时间点聚集条目数超阈值 | 提示 |

两个关键设计：

1. **写入后同步体检 + 定时全量巡检**。前者保证新问题立刻可见，后者保证历史数据与新增规则同样被覆盖。
2. **收敛而非累积**：`fingerprint` 唯一索引防重复告警；每轮体检后，
   本轮未复现的 `open` 异常自动置为 `resolved`。因此收件箱里剩下的每一条都代表**此刻仍然存在**的问题，
   不会变成没人看的噪音坟场。

阻断级异常会挂住「标记已校验」（`Event::hasBlockingAnomalies()`），
让「有问题但被标成已校验」在流程上不可能发生。

### 5.5 冲突处理决策树

```
用户点保存
  │
  ├─ 权限 / 状态 / 出处范围不允许 ──────────► 403 + 具体原因（不是笼统的「无权限」）
  │
  ├─ version 匹配 ─────────────────────────► 写入成功，生成新 revision
  │
  └─ version 落后 ─► 409 + 字段级 diff
        │
        ├─ 无字段冲突 ───────────────────► 「双方改动互不重叠」→ 一键合并
        └─ 有字段冲突 ───────────────────► 合并面板：逐字段裁决 → 以最新版本重写
```

### 5.6 失败模式与对策

| 失败模式 | 对策 |
| --- | --- |
| 两人同时编辑同一条目 | 乐观锁 CAS；后者不覆盖，进入合并流程 |
| 两人改到同一个字段 | 字段级三方 diff，人工裁决，两侧输入都不丢 |
| 两人改不同字段 | 自动合并，无需人工介入 |
| 用户关掉页面留下「正在编辑」 | 租约自动过期回收；且不影响他人写入 |
| 有人录入了错误的时间 | 版本链可回滚（回滚生成新版本，历史不覆盖） |
| 两条冲突规则在群里吵不出结果 | 条目置为 `disputed` 冻结正文，annotation 集中讨论，reviewer 裁定 |
| AI 产出了看似合理的假事件 | 提案制 + 四层校验 + 硬闸门 + 审核留痕 |
| 重新解析规则后发现历史数据不符 | 定时全量巡检 + `--rebuild` 重算纪元归属 |
| 有人删错条目 | 软删除 + 版本链可恢复（需 reviewer） |

### 5.7 已知边界

诚实列出当前没有做的事，避免被误读为「已经解决」：

- **正文级内容冲突**不做自动合并。两个人都重写了 `details` 时只能人工裁决，不做文本 diff 合并。
- **没有实时协同编辑**（无 OT/CRDT）。多人同时编辑同一条目靠乐观锁 + 合并，而不是实时同步。
- **相对时间只解决了「解析与标记」**，锚点自动回填尚未实现：`precision = relative` 的条目会先进入「时间未定」泳道，并由巡检告警，等人工指定锚点。
- **一致性巡检是规则式的**，不是语义推理。它能发现「结果早于起因」，但发现不了「起因与结果其实无关」。
- **种子数据集是起始语料，不是权威年表**。其中大量条目在社区考据中属于推断而非官方明写 —— 这正是产品要解决的问题本身，条目上的 `date_confidence` 会如实标注。
