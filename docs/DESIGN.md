# 明日方舟时间线 · 设计说明

《明日方舟》统一事件时间表。本文回答四件事：**怎么用（交互）**、**数据长什么样（结构）**、
**谁能改什么（权限）**、**AI 怎么接入以及怎么保证多人编辑下时间线不崩（一致性与冲突）**。

---

## 0. 出发点是三个现实约束

设计中的所有取舍都来自这三个约束，先讲清楚，后面的决策才不是凭空来的。

| 约束 | 表现 | 对设计的影响 |
| --- | --- | --- |
| **泰拉历不是可用历法** | 「1096年12月23日」「1097年冬」「1098年」「纪元前（年表未载）」并存，还有大量相对时间 | 时间必须以**区间 + 精度 + 可信度**建模，不能落成 datetime |
| **内容天然不可信** | 官方明写、设定集推断、社区考据混杂，彼此矛盾 | 每条时间都带 confidence，并区分「已确证 / 推断 / 存疑」 |
| **协作方是考据者，不是运维** | 他们会改错、会重复录、会中途关页面 | 不能靠硬锁与互斥；要靠可见性、可回滚与收敛式巡检 |

## 1. 交互设计

### 1.1 信息架构

```
/                     时间线（公开可读）
  ├─ 左侧筛选栏       时间轴 / 纪元 / 出处 / 阵营人物 / 标签 / 状态
  ├─ 中部时间线       按纪元分组的条目流 + 顶部时间轴概览
  └─ 右侧抽屉         条目的查看 / 编辑 / 标注 / 版本
/sources              出处与语料库（AI 梳理的输入源）
/sources/{slug}       单个出处：原文录入 + 触发梳理 + 该出处条目
/proposals            AI 审核台（提案队列 + 梳理表单）
/anomalies            一致性收件箱（巡检产出的异常）
/admin/users          账号管理（仅管理员）：搜索筛选表格 + 批量操作 + 弹窗表单
/admin/users/{id}     账号详情：基本资料 + 贡献统计 + 操作日志
/login                登录
```

五页的划分对应五种角色动作：**读**（时间线）、**写**（抽屉）、**灌语料**（出处）、
**裁决**（审核台 / 收件箱）、**管人**（账号管理）。
刻意没有把 AI 审核台做成时间线的一个模式 —— 它是「AI 内容进入时间线前必须经过的关卡」，独立成页才有仪式感与责任感；
账号管理同样独立，因为它是唯一会改变「谁能进来」的地方。

### 1.2 时间线页

- **纪元色带分组**：条目按所属纪元成组，组头显示纪元名、区间与条数。纪元的颜色贯通筛选器、缩放条与卡片，形成空间记忆。
- **缩放条（canvas）**：把全站条目按年聚合成直方图，纪元以色带铺底。**拖选一个区间即等于一次时间筛选**，是「先看分布、再钻细节」的主路径。
- **「时间未定」独立泳道**：未定位时间的条目统一排在最后，不插入时间序列。原因是把未知混进有序列表会污染排序语义 —— 用户会误以为它「发生在 0 年」。
  这条泳道不是兜底容器，而是**一等公民**：官方世界观设定集（如《大地巡旅》）的主体内容是世界机制与国家背景，
  年份普遍未载，因此它的绝大部分条目天然属于这里。泳道同时是「待考据」的工作队列。
- **条目标记语言**：
  - 左侧时间轴节点颜色 = 时间可信度（绿=已确证 / 黄=推断 / 红=存疑）
  - 卡片左边框 = 状态异常（红=一致性告警 / 黄=冻结）
  - 徽章区直接展示精度、可信度、告警数、锁定态
  - 纪年原文永远以等宽字体原样显示，**不做任何「友好化」改写**
- **详情抽屉四页签**：详情（含出处引文）/ 编辑 / 标注 / 版本。信息与操作分离，读的时候不会被表单干扰。
- **编辑即声明基线**：编辑页顶部明确写出「本条目当前版本 v12，保存时会携带该版本号」，让并发规则对用户可见，而不是失败后才解释。
- **冲突面板**：不做「保存失败，请刷新」这种丢输入的处理，而是把字段级三方 diff（基线 / 对方 / 我方）铺开，未打架的改动自动并入，只让用户裁决真正打架的那几个字段。
- **标注入口对所有访客开放**：纠错的门槛必须低于改正文的门槛，否则时间线的纠错回路会断。编辑页不可用时，会提示改走标注通道。

### 1.3 AI 审核台

三段式：**触发区**（选出处 / 粘原文 / 定目标纪元）→ **队列区**（状态计数 + 批量采纳）→ **提案卡**（折叠展开）。

每张提案卡展开后必须能回答「我凭什么信它」，因此固定包含：

1. 阻断与待补正问题（硬闸门 / 软闸门分开呈现）
2. 摘要
3. **出处核验**：逐条引文标出「已在原文定位 ✓ / 原文中找不到 ✗」与字符偏移
4. **校验明细**：结构、时间可解析、出处定位命中数
5. **一致性预检**：时代错位 / 疑似重复 / 锚点失效
6. 关联人物、阵营、建议标签
7. 模型原始返回（可展开）
8. 操作：采纳为新建 / 合并进既有 / 驳回（必填理由）

### 1.4 视觉与可用性

基调对齐《明日方舟》官方站的排版语言。其中四条来自官方站文本层的**可确证**特征：

1. **双语并列**——全大写英文微标签 + 中文主标题（`Timeline // 时间线`、`OPERATOR / 干员`）
2. **`//` 是全站系统级分隔符**（`Terra Timeline ://`、`00 // 00 / 05`、`2026 // 09 / 23`）
3. **编号与计数仪表**（`TOTAL 51 // SHOWN 40`、`CNT 05`、`VER 04`）
4. **`[方括号]`包裹实体标签**（`[已校验]`、`[推断]`）

色值与形状语言取自品牌视觉：近黑中性底（`#0d0d0d`，不带蓝味）+ 白 + 标志黄（`#ffd400`）三色为主，
**直角为默认**，仅实心主按钮与品牌标记做单角斜切；纪元配色采用**单一色族递进梯度**
（远古灰 → 深黄 → 标志黄 → 琥珀 → 橙 → 红），靠明度与暖度区分而非堆砌色相。
界面不引用任何官方素材，配色由 CSS 变量与数据库字段驱动。

一条硬约束：**`//` 日期母题只用于元数据**（版本时间、标注时间、公告时间）。
条目的游戏内纪年 `date_display` 永远原样输出——泰拉历的粒度本身就是信息，重排它等于伪造精度。

- 无构建步骤：容器内没有 Node，因此手写 CSS 与原生 JS，由 `<body data-page>` 分派页面逻辑；
  「技术化仪表」的观感靠等宽字体、字号对比、字距、直角与网格底纹实现，而非下载 webfont，保证离线可用。
- 空状态都给出下一步动作（空时间线 → 引导去 AI 梳理；空提案区 → 引导粘贴语料）。
- 数据库中由用户自定的颜色（阵营、标签）统一在 CSS 里降饱和处理，使任意配色都能落进这套底色而不打架。
- Esc 关闭抽屉与冲突面板；抽屉打开时自动获取编辑租约。

## 2. 数据结构

### 2.1 时间模型（最关键的一张表）

时间存为**闭区间** `[start_index, end_index]` 加两个枚举，而不是单个时间戳：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `date_display` | string | **原始纪年文本**，展示层只认它 |
| `start_index` / `end_index` | integer | TerraDate 网格索引，可比较、可聚合 |
| `date_precision` | enum | day / month / season / year / range / relative / unknown |
| `date_confidence` | enum | confirmed / inferred / disputed / unknown |

网格索引是单调递增的整数，与公历闰年、月末无关：

```
index = year * 372 + (month - 1) * 31 + (day - 1)
```

**为什么不用 Carbon。** 把「1097年冬」存成 `1097-12-01` 就是伪造精度：它会让排序看起来更整齐，
但在「1098 年 1 月是否属于 1097 年冬」这类判断上直接出错，而且用户无法察觉。
用整数网格 + 区间语义，精度不足只体现为「区间更宽」，语义始终正确：

```
day     → [d, d]
month   → [月初, 月末]
season  → 春=3–5月  夏=6–8月  秋=9–11月  冬=12月–次年2月（跨年，月份允许 > 12）
year    → [1月1日, 12月31日]
range   → 显式区间
relative→ 索引置哨兵 0，等锚点事件确定后再回填
unknown → 索引置哨兵 0，归入「时间未定」泳道
```

**区间查询用重叠而不是包含**：`end_index >= from AND start_index <= to`。
这是「1097年冬」能被「1098年1月」命中的唯一原因，也是最容易被写成 bug 的地方（有测试专门守着）。

**排序是全序且稳定的**：

```sql
ORDER BY (date_precision = 'unknown') ASC,  -- 未定位排最后
         start_index ASC, sort_seq ASC, id ASC
```

第一顺位用 CASE 把未定位条目踢到最后：若只按 `start_index` 排，它们（索引 0）会插在「纪元前」（负索引）与「1038 年」之间。

**展示层永远回落到 `date_display`**，绝不从索引反推格式化 —— 一旦反推，就又会伪造精度。

### 2.2 字典层

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `eras` | name, slug, date_label, start_index, end_index, color | 时期切分。区间用于「时代错位」巡检 |
| `factions` | name, parent_id, color | 支持层级；筛选按母阵营时向下包含子阵营 |
| `characters` | name, codename, faction_id | 人物 |
| `sources` | name, type, code, chapter, release_order, **raw_text** | 出处。`raw_text` 是溯源链的根 |
| `tags` | name, color | 人工自由标注维度 |

`sources.raw_text` 是整个机制的地基：AI 抽取出的每条引文都要回到这段文本做字符偏移定位，
人工也能顺着偏移点回原文核对。因此把原文录进系统本身就是一项有价值的工作。

### 2.3 核心表 `events`

按用途分四组字段：

```
内容      title / summary / details / location
时间      date_display / start_index / end_index / date_precision / date_confidence / era_id / sort_seq
结构      parent_event_id（归纳） / caused_by_event_id（因果）
协作      status / version / is_locked / created_by / updated_by / verified_* / deleted_at
```

`parent_event_id` 与 `caused_by_event_id` 不是装饰：它们是「因果倒置」「子早于父」两类巡检的判据，
没有这两个字段，语义一致性问题就只能靠人眼发现。

### 2.4 关系层与协作层

关系表（`event_source` / `event_character` / `event_faction` / `event_tag`）都是**关系表 + 元数据**，
而不是 JSON 列 —— 只有这样才能按维度建索引检索（「按阵营筛选」是最常用的入口之一）。

| 表 | 作用 |
| --- | --- |
| `event_revisions` | 全量版本快照。三重用途：审计、三方合并的 base、回滚 |
| `annotations` | 标注 / 纠错建议，访客可用 |
| `event_locks` | 编辑租约（软锁），不阻塞但可见，到期自动回收 |
| `ai_proposals` | **AI 产出暂存区**，AI 永不直接写 events |
| `timeline_anomalies` | 一致性异常收件箱，`fingerprint` 唯一索引防重复告警 |
| `source_user` | 出处归属，用于限制编辑者的改动范围 |

`event_revisions` 上有 `unique(event_id, version)`。这个约束不是装饰 —— 它保证了「一个版本号只对应一次写入」，
任何试图在同一版本写两条记录的代码都会立刻失败（开发期就撞到过，见 §5.3）。

## 3. 权限、账号与数据边界

这一章覆盖三件互相牵连的事：谁能改（角色矩阵与三层叠加约束）、
谁能进（账号体系与外部身份）、以及**什么能放在一起比**（世界维度）。
后两节看起来不像是「权限」，但它们决定的都是同一类问题：
一条数据在什么条件下才成立。

### 3.1 角色与能力矩阵

表头第一行是枚举值（与数据库、代码里一致），第二行是界面上的展示名
（取自《明日方舟》世界观里的罗德岛编制序列）：

| 能力 | viewer<br>预备干员 | editor<br>干员 | reviewer<br>精英干员 | admin<br>博士 |
| --- | :-: | :-: | :-: | :-: |
| 浏览时间线 / 检索筛选 | ✔ | ✔ | ✔ | ✔ |
| 提交标注（评论、纠错、存疑） | ✔ | ✔ | ✔ | ✔ |
| 新增 / 修改 / 删除条目 | — | ✔ | ✔ | ✔ |
| 发起 AI 梳理（产出提案） | — | ✔ | ✔ | ✔ |
| 查看审核台 | — | ✔ | ✔ | ✔ |
| **采纳 / 合并 / 驳回 AI 提案** | — | — | ✔ | ✔ |
| 标记「已校验」、裁定争议 / 废弃 | — | — | ✔ | ✔ |
| 锁定 / 解锁条目 | — | — | ✔ | ✔ |
| 处置一致性异常、强制接管编辑租约 | — | — | ✔ | ✔ |
| 回滚历史版本、恢复已删条目 | — | — | ✔ | ✔ |
| 管理用户 / 字典 | — | — | — | ✔ |

三条刻意设计：

1. **读永远开放**。考据项目的价值来自可被引用，不能先登录再看。
2. **看提案 ≠ 放行提案**。editor 可以看提案、可以跑梳理（产出必然停在待审），但只有 reviewer 能把 AI 内容写进时间线。
3. **标注对所有人开放**，包括未登录访客（`user_id` 记 null 以示区别）。

### 3.2 权限的三个叠加约束

即便角色够，还要同时满足：

- **条目状态**：`disputed` / `deprecated` 的条目正文冻结，editor 只能提交标注建议；reviewer 可直接改。
- **条目锁定**：reviewer 锁定后，editor 连改都改不了（常用于争议条目的集中讨论期）。
- **出处归属**：`users.strict_source_scope` 开启时，editor 只能改自己负责的出处（`source_user`）相关条目。
  未归属任何出处的条目对所有 editor 开放，避免出现「无主的条目谁也改不了」。

### 3.3 权限判定的默认方向

`User` 模型上显式声明了 `$attributes = ['role' => 'viewer', 'strict_source_scope' => true]`，
并提供 `enforcesSourceScope()` 把 null 当 `true`。

原因是实测踩到的：`User::create([...])` 不会把未提交的列补进属性数组，
于是 `$user->strict_source_scope` 会读到 null，而 `null` 是 falsy —— 出处范围限制被静默绕过。
**权限判断的默认方向必须是更严，而不是更松**，这一条写进了模型注释与测试。

### 3.4 账号管理：三条防「把自己锁在门外」的硬约束

用户管理最容易出的不是功能缺陷，而是权限事故。三条约束集中在 `UserManager`
（账号写入的唯一入口，与 `EventWriter` 同构），每条都对应一个真实事故场景：

| 约束 | 事故场景 |
| --- | --- |
| **删除 / 禁用自己一律拒绝** | 这两种操作会立刻让自己失去访问权，几乎只可能是误点 |
| **不能掏空最后一个启用中的管理员** | 若允许，系统会进入「谁都进不了管理页」的死局，只能改库 |
| **一切变更留痕** | 「谁在什么时候改了什么」是账号维度最容易说不清的问题 |

几处刻意的设计：

- **不变量用统一检查而不是各处特判**。「降级自己」为什么被拦？不是因为「自己」这个身份，
  而是因为它会让启用中的管理员归零。把这条写成 `assertNotLastActiveAdmin()` 之后，
  它是唯一且可测的规则，将来放宽自保护也不会失守。
- **两层判定各司其职**。`UserPolicy` 负责「角色够不够」并给视图提供按钮可见性，
  自保护两条返回 `Response::deny('原因')` 而不是 `false` —— 空的 403 会让人以为是权限配错了；
  `UserManager` 再守一次真正的跨行不变量，因为策略可能被绕过（命令、队列、新入口）。
- **禁用必须立刻生效**。Laravel 的 session guard 只在登录那一刻验凭据，
  因此加了 `EnsureAccountIsActive` 中间件在每个已登录请求上复核状态 ——
  否则「刚被禁用的人」能靠既有会话继续写入到会话自然过期。
- **删除是软删除**（与 `events` 一致），因为本项目的核心价值是「谁改的」：
  硬删除会把 `events.created_by` / `event_revisions.user_id` 等外键置空，等于抹掉归属。
  代价是邮箱唯一索引仍被占用，因此校验必须包含软删除行并提示「可先恢复该账号」——
  校验若放行而数据库唯一索引拒绝，用户拿到的是 500 而不是可读的提示。
- **重置密码只回显一次**。管理员无法查看既有密码（哈希不可逆），只能重置为新的随机密码；
  明文仅在响应里出现一次，界面再用一次性弹窗承接（`data-after-close="reload"` 保证
  无论用哪种方式关窗都会刷新列表）。
- **操作日志的列名叫 `field_changes` 而不是 `changes`**：Eloquent 的 `HasAttributes`
  自带 `protected $changes`，重名会导致「类外走 `__get` 拿到数据库列、类内直接命中内部空数组」
  的分裂行为，且不报任何错。为此补了 `ModelAttributeCollisionTest` 用反射守住所有模型。

### 3.5 账号体系：昵称与登录名分离、头像、外部身份

#### 昵称与登录名为什么必须分开

`users.name`（登录名）是**凭据**，`users.nickname`（昵称）是**展示名**。两者各自全服唯一，
但规则完全不同 —— 因为「能拿来登录」和「能拿来显示」对字符集的要求是相反的：

| | 登录名 `name` | 昵称 `nickname` |
| --- | --- | --- |
| 字符集 | 仅 ASCII：`^[A-Za-z][A-Za-z0-9_-]{2,29}$` | 任意（含中文） |
| 大小写 | 统一转小写存储 | 保留原样，但唯一性**不区分**大小写 |
| 用途 | 登录、URL、@提及 | 时间线与日志上的展示 |

限制登录名为 ASCII 有两个具体理由：**同形字攻击**（西里尔字母的 `а` 与拉丁的 `a`
在多数字体里无法区分，`аdmin` 与 `admin` 就成了两个账号），以及**歧义**——
「邮箱或登录名都能登录」这条规则只有在登录名不含 `@` 时才成立。

统一转小写存储则是为了**跨数据库一致**：MySQL 的 `utf8mb4_unicode_ci` 不区分大小写，
SQLite 的 TEXT 区分。同一份数据在测试环境与生产环境的唯一性判定不同，是最难排查的一类问题；
全部落成小写之后，`Admin` 与 `admin` 就是同一个字符串，讨论才成立。

昵称虽然不区分大小写，但**保留原样**（`考据员A` 不会变成 `考据员a`），
并且写入前会把连续空白折成一个空格 —— 否则「考据 员」与「考据  员」会是两条不同记录，
而人眼完全分不出来。唯一索引本身挡不住这种重名。

#### 唯一性必须包含软删除行

`users.name` 与 `users.nickname` 的唯一索引都**不排除软删除的账号**：被删除的账号
仍然占着它的名字。这是有意的 —— 恢复账号时不必重新协调命名，也防止
「删掉某人再用同名注册」这种身份冒用。

代价是**校验与索引必须严格一致**：校验一旦放行而索引拒绝，用户拿到的是 500。
因此这里没有用 `Rule::unique`，而是写了 `App\Rules\UniqueNickname` 显式 `lower()` 比对，
并统一通过 `User::scopeWhereNicknameIs` 一类的查询作用域实现 —— 校验层与
「并发冲突后重查定位字段」那段代码共用同一套语义。

#### 头像为什么重新编码、为什么不交给 web 服务器

上传的图片是**不可信输入**，本项目的处理是三件事叠加：

1. **一律重新编码**（`AvatarService`）。上传的文件可以同时是合法 JPEG 和合法 ZIP
   （多态文件），原样落盘再交给浏览器就多一条攻击路径。经过 GD 解码再编码只保留像素，
   EXIF（含 GPS 坐标）与任何附加数据都被丢掉，顺带完成了居中裁剪与缩放到 256×256。
2. **白名单里没有 SVG**。这里有个容易踩的坑：Laravel 的 `image` 规则**允许 svg**
   （它的实现是一份含 svg 的 mimes 白名单），而 SVG 可以内嵌 `<script>`，
   被浏览器当图片加载时照样执行。因此 `UploadAvatarRequest` 里 `image` 与
   `mimes:jpg,jpeg,png` 必须**同时存在**，后者才是真正的闸门。
3. **由 `AvatarController` 受控输出**，而不是写进 web 根目录或依赖 `storage:link`。
   前者是「上传目录在 docroot 里」这一经典 RCE 模式的变体；后者少一个
   「部署时忘了执行就整站头像 404」的隐性步骤。控制器里 `Content-Type` 与
   `X-Content-Type-Options: nosniff` 都是写死的，即使校验被绕过、目录里出现了一个
   HTML 文件，它也只可能以 `image/jpeg` 返回。URL 里的 `v` 段是内容指纹而非权限凭据，
   因此可以放心给响应打一年的 `immutable` 缓存。

输出统一为 JPEG 是因为容器里的 GD **没有编译 WebP**（`gd_info()` 的 WebP Support 为空）。
PNG 的透明区域会先被压平到站点面板色 `#1b1b1b`，否则在 JPEG 里会变成纯黑，
在深色界面之外看起来像图片坏了。

#### 三条注册路径共用同一套不变量

账号的产生方式有三条：管理员建号（`UserManager::create`）、网页自助注册
（`UserManager::register`）、外部渠道注册（`UserManager::registerExternally`）。
后两条走同一个私有实现 `createSelfServiceAccount()`，差别只有两点：
密码从哪来、日志怎么写。

这不是为了少写几行 —— 拆成两份实现迟早会分叉，而分叉的那一侧几乎总是权限更松的那一条。
共用的部分包括：角色硬编码为 `viewer`（自助注册的账号不能自己决定权限）、
`strict_source_scope` 固定开启、`email_verified_at` 留空（没有验证链路就不假称已验证）。

命名相关的校验同理，四个入口共用 `ValidatesAccountNaming`：
`name` / `nickname` / `email` 必须在**每个入口**都与数据库唯一索引严格对齐
（包含软删除行、昵称不区分大小写、登录名统一小写）。
这份规则散在四个文件里时，漏掉任何一处的结果都是「校验放行 → 插入撞索引 → 500」。

`/register` 是全站唯一一条**匿名用户能直接触发账号表写入**的路径，因此三道闸门叠加：
路由上的 `throttle:10,1`（按 IP 限流，挡批量刷号）、`RegisterRequest`（命名与唯一性）、
`UserManager` 的不变量（角色与编辑范围）。限流这一道不能省：没有它，
一个脚本就能以每秒几十个的速度建号。

「是否开放注册」是运营决定而不是技术决定，因此做成 `config/identity.php` 里的开关
（`IDENTITY_REGISTRATION`，默认开放）。关闭后注册页与提交入口一起拒绝 ——
只把链接藏起来不算关闭。

#### 外部身份：能做什么、刻意不做什么

`user_identities` 表统一承载所有外部渠道，两条唯一索引分别保证
「一个外部账号只能属于一个本地账号」与「每个渠道只能绑一个」。

几条刻意的边界：

- **不存任何外部令牌**（没有 `access_token` / `refresh_token` / `raw` 列）。
  外部身份在本系统里只用于回答「你是谁」，不会拿令牌代用户调用对方接口；
  存下用不到的令牌只会扩大泄露影响面，属于净负债。
- **绝不代收外部账号密码**。绑定只能由用户在自己的浏览器里完成授权。
  「输入你的鹰角密码，我帮你绑定」这种模式不是实现起来麻烦，而是从根本上不该做。
- **邮箱撞车时拒绝静默并号**。外部渠道只断言「他是某个外部账号的持有者」，
  我们并没有验证对方返回的邮箱归属（本项目也没有邮件验证流程）。若按邮箱自动并号，
  任何人只要在某个渠道上把邮箱填成受害者的，就能直接接管本地账号。
  正确路径是：先用邮箱登录，再到设置里主动绑定。
- **state 一次性消费**（`session pull`）、只保留最近 5 条、10 分钟有效。
  一次性是为了防重放（用户刷新回调页不该被接受第二次），上限是为了让反复点击
  登录按钮不会把会话撑大。**顺序不能反：先验 state，再用 code** ——
  code 是可被重放的凭据。
- **绑定会校验「发起人 == 回调时的登录人」**。否则会出现这种错位：
  A 发起绑定 → 同一浏览器上 B 登录 → 回调把外部身份绑到 B 名下，
  而 A 的外部账号从此归 B 所有，两个人都看不出发生了什么。

#### 关于「绑定鹰角账号」的现状

**鹰角网络没有提供面向第三方的公开 OAuth 接口。** 因此本项目的做法是：

- **不预置任何猜测出来的端点**。逆向其私有接口既违反服务条款，也会随对方改版随时失效。
- 渠道走同一套配置驱动的 OAuth2 流程（`config/identity.php` 里的端点与字段映射），
  一旦拿到正式凭据，只需填 `HYPERGRYPH_*` 环境变量即可启用，**不需要改代码**。
- 在凭据到位之前，「绑定鹰角账号」走 `allow_manual` 的**手工登记**路径：用户提交通行证
  UID，落库为 `pending`，由管理员在账号详情页核验后转 `verified`。
  界面上「待核验」与「已核验」始终分开显示 —— 自助声明不能表现为认证，
  否则等于系统在替用户背书。核验本身是人工判断，不代表鹰角网络官方认证。
- 本地演示渠道 `stub` 让整条链路在没有真实凭据的环境里也能走通，
  它对任何点一下的人都放行，因此 `enabled` 与环境绑定（只在 `local` / `testing` 为真），
  配置缓存时会固化成 `false`。

#### `password_set_at`：为什么不能靠 `password` 列判断

外部渠道注册的账号也有密码哈希（随机占位值），但**本人永远不知道它**。
若只看 `password` 列非空，系统会误判「他有密码，可以解绑最后一个身份」，
结果把人永久锁在门外。因此单独用一个时间戳只回答「密码有没有被设置为本人可知的值」，
`IdentityManager::unlink` 的守卫依据它决定是否拒绝。

### 3.6 世界维度：为什么塔卫二不能和泰拉共用一条时间轴

加入《明日方舟：终末地》的塔卫二年表时，最省事的做法是「再加一批事件」。
但那样做出来的东西会**看起来正常、实际毫无意义**，而且不会报任何错。
原因是这个系统的排序键：

```
index = year * 372 + (month - 1) * 31 + (day - 1)
```

它是一个**没有量纲的整数网格**。泰拉历 1097 年的索引是 405,702，
塔罗斯历 5 年的索引是 1,860 —— 两个数字之间不存在任何可比关系，
但 ORDER BY 照样会给出一个结果。这就是世界维度必须存在的唯一理由。

### 具体会错在哪里

不是理论风险，而是已经能指出行号的那种：

| 位置 | 少了世界条件会发生什么 |
| --- | --- |
| 时间线查询 | 两个世界的条目被排进同一条序列，分页与「年代分布」统计整体失真 |
| 纪元自动归属（`reindexEraAssignments`） | 泰拉第一个纪元「远古 · 前纪元」覆盖 `-186000 ~ 371627`，**塔罗斯历 5 年的 1,860 落在里面** —— 塔卫二的条目会被静默归入泰拉的远古纪元 |
| 纪元区间不重叠校验 | 跨世界比较，把互不相干的区间判成重叠 |
| 疑似重复检测 | 先按时间区间重叠筛候选，跨世界会把索引相近的条目拉进同一个候选集 |
| 单日过载检测 | 「索引相同」只说明在各自的纪年里落在同一天，跨世界计数纯粹是噪声 |
| 时间轴刻度与回溯文案 | 塔卫二的条目会显示成「约泰拉历 152 年 3 月」—— 一个彻底的错误信息 |

### 因此定下的三条硬约束

1. **`scopeOfWorld()` 的参数不可为空**（`Event` / `Era` / `Source`）。
   把世界设成必填，是为了让「忘记按世界隔离」在调用点就写不出来 ——
   这类遗漏不会报错，只会给出错误答案，所以只能靠签名挡住。
2. **条目的世界不可更改**（`EventWriter::assertWorldUnchanged`，显式拒绝而不是忽略字段）。
   换世界等于换一套纪年：`start_index`、纪元归属、出处引用会同时失去意义。
   正确做法是新建条目。
3. **纪元必须与条目同世界**（`EventWriter::assertEraBelongsToWorld`）。
   否则 `coversIndex()` 会拿塔罗斯历的索引去比泰拉纪元的区间 ——
   时代错位校验会退化成一台随机报警器。

### 哪些东西**不**按世界切分

- **阵营与人物是共享词典**。罗德岛同时存在于两个世界的历史里（终末地工业由它协同组建），
  强行切分反而会把同一个组织拆成两份。筛选下拉按「在这个世界里出现过」收敛，
  因此整合运动不会出现在塔卫二的选项里，而罗德岛两边都在。
- **出处只在筛选层面分世界**，不做引用完整性约束：一份泰拉设定集完全可以记到塔卫二的事，
  因此没有「出处必须与事件同世界」这条不变量。
- **标签保持全局**：它是跨世界的横切概念（天灾、源石、星门）。

### 塔罗斯历的年份只有一两位数，由此牵出的一处连带修改

塔卫二的纪年叫**塔罗斯历**，年份是 1、5、75、152 这种一两位数，
而原有的解析器把年份硬编码为 `\d{4}`。放宽成 `\d{1,4}` 之后，
「切尔诺伯格事变前 3 年」里的 3 也会被 `parseYear` 当成绝对年份 ——
而 `parseYear` 恰好排在 `parseRelative` 之前（这个顺序本身是为了让
「泰拉历前 200 年」不被误判成相对时间）。

解决办法是把判断显式化：`parse()` 在进入绝对日期解析之前先检查
「这是不是相对时间」。判据用同一个正则常量（`RELATIVE_PATTERN`），
并排除纪元前年份 —— 两者的区别很明确：「纪元前」的「前」紧贴历法名或串首，
而相对时间的「前 / 后」前面必须有 2-24 字的锚点。

### 3.7 干员简介：为什么不在这里维护人物档案

`/operators` 只做三件事：列出人物、写一行与时间线相关的简介、**把人送到 PRTS 维基**。

这不是「省事」，而是这个项目自身逻辑的推论。整个系统的价值建立在
「每条结论都能追溯到出处」上（见 §2 的时间模型、§4 的引用可定位校验）。
而一份抄自别处、又落后于对方更新的人物档案，恰好是这套体系里**最无法追溯的东西**：
它看起来像考据结论，实际上既没有引文，也没有人会来更新它。

因此定下三条边界：

1. **本地只写一行「与时间线相关」的简介**（`characters.description`），
   内容限定为身份定位（谁、属于哪方），不做剧情总结。种子数据里只为核心人物撰写，
   其余留空 —— 留空是常态，不是缺陷。
2. **没写过简介时不由系统编一句**。`Character::profileText()` 会退回由
   阵营 / 种族 / 条目数拼出的「事实卡」，界面上同时标注
   「本仓库还没有为这位人物写过简介 —— 上面那段是结构化字段，不是考据结论」。
   系统可以少说，但不能说得像结论。
3. **外链是显式配置的，且按世界指向各自的权威维基**，不是从名字硬拼、也不是统一指向 PRTS：

   ```
   页面标题 = wiki_slug ?: name        // 默认可推导
   URL      = config('timeline.character.wikis.<该人物的 world>.base') + rawurlencode(标题)
   ```

   泰拉干员 → PRTS 维基（`wikis.terra.base`），塔卫二人员 → 终末地 WIKI（`wikis.talos.base`）。
   对方的命名空间不归我们管，所以「默认能推导」与「必须可覆盖」
   两件事都要成立 —— `wiki_slug` 就是那个覆盖开关。
   外链一律 `target="_blank" rel="noopener noreferrer"`（避免把本站地址与
   `window.opener` 交给外部站点）。

相关条目按世界分组，理由与 3.6 相同：罗德岛这类人物同时存在于两个世界的年表里，
而两套纪年不可比，混成一条序列会让读者误以为先后关系是有意义的。

## 4. AI 补全：触发与校验

### 4.1 铁律

> **AI 的任何输出都只能落在 `ai_proposals`。`events` 表只能由人工在审核台放行后写入。**

原因：幻觉在产品层的表现不是报错，而是时间线上多出一条「看起来完全合理」的假事件，
比缺失更难被发现。所以宁可牺牲自动化程度，也要保住这一道人工关卡。

### 4.2 触发方式

| 方式 | 入口 | 说明 |
| --- | --- | --- |
| 出处补全 | 出处详情页「开始梳理」 | 用 `sources.raw_text` 整段作为输入，最常用 |
| 即席梳理 | 审核台粘贴文本 | 临时片段，可选回写到出处（便于后续复现与定位） |
| 报告式补全 | 审核台选择出处 | 不粘文本，直接跑该出处已存语料 |
| 自动触发 | 新建出处且已填 `raw_text` | 走队列，避免长请求阻塞（预留 `SynthesizeEventsJob` 位置） |

### 4.3 驱动抽象与降级

```
AiDriver (interface)
  ├─ HeuristicAiDriver      纯规则离线抽取，零依赖零成本
  └─ OpenAiCompatibleDriver 任意兼容 /chat/completions 的服务
```

`heuristic` 驱动的定位不是「假装是 AI」：它按纪年表述切出候选窗口，既能在没有密钥时兜底，
也能作为 LLM 的前置过滤器把 token 消耗砍掉一个数量级，还能作为判定「模型出问题还是语料出问题」的基线。

配置了 `openai-compatible` 但**没填密钥时会静默降级到 heuristic 而不是抛异常** ——
AI 梳理是增强功能，它挂掉不该让整个站点不可用。

提示词里三条硬要求都是为了配合下游校验：强制 JSON、强制提供**逐字原文引用**、注入既有条目清单以抑制重复。

### 4.4 四层校验

任何一层不过，都进不了 `events` 表。

| 层 | 内容 | 不通过的后果 |
| --- | --- | --- |
| **L1 结构** | 必填字段非空、`confidence` 落在 0–100、数组字段结构正确 | 直接丢弃，不生成提案 |
| **L2 时间可解析** | `date_display` 必须能被解析出网格索引 | 记为「需补正」，禁止直接入库 |
| **L3 出处可定位** | 每条 `evidence.quote` 必须在 `raw_text` 中定位成功（归一化子串匹配，容忍空白与标点差异，**不容忍改写**），并回填字符偏移 | 记为 `unverified`，**硬闸门** |
| **L4 一致性** | 只读预检：时代错位、疑似重复、相对时间锚点失效 | 阻断级问题禁止直接入库 |

外加**批次内去重**与**与既有条目去重**（2-gram Jaccard + 包含关系提权），重复项落为 `duplicate` 并挂上 `duplicate_of_event_id`。

校验结论全部写进 `ai_proposals.validation` 一并持久化，因此审核人可以离线复现「当时为什么被判为有问题」。

### 4.5 闸门的两级设计

初版把所有问题放进一个 `blockingIssues()`，结果发现一个漏洞：**审核人只要传任意 `overrides` 就能绕过出处校验**，
顺手改个标题就把一条毫无出处的幻觉内容放进了时间线。修正为两级：

- **硬闸门（hardIssues）**：只有「缺少可定位的原文引用」一条。
  不可被 `overrides` 绕过，必须显式传 `acknowledge_missing_evidence = true` 才能放行，
  且审核记录里会留下「⚠️ 已确认该提案无原文出处支撑」的免责痕迹。
- **软闸门（softIssues）**：时间不可解析、一致性阻断。允许审核人**补正字段后**放行，
  但「什么都不改直接放行」依然被拒。

### 4.6 审核动作与反馈闭环

- **采纳为新建**：生成条目，状态固定为 `needs_review`（还需人工再点一次「标记已校验」），
  revision 的 `origin = ai`、`user_id = 审核人` —— 「谁为这条 AI 内容负责」永远有答案。
- **合并进既有条目**：不丢信息。提案里的出处引文与关联人物会**追加**到目标条目，
  并留一条 annotation 说明来源。
- **驳回**：理由必填，写入 `review_note`，作为 prompt 调优的反馈数据集。

采纳后还会把该条目的一致性异常 `ai_proposal_id` 回填，方便日后复盘「哪一批 AI 产出更容易出问题」。

## 5. 多人编辑下的一致性与冲突处理

冲突分成三个层次，**用三种不同的机制分别解决** —— 试图用一个机制包打天下是这类系统最常见的失败。

### 5.1 结构层：时间线不会被「拆断」

**做法：排序是派生量，不是存储量。**

条目的顺序由 `(start_index, sort_seq, id)` 在查询时计算得出，表里没有 `prev_id` / `next_id` 这类链表字段。
因此：

- 并发插入两个「1097 年 3 月」的条目，不需要任何协调，两者的相对顺序由 `id` 决定，都是合法结果；
- 分页是稳定的 —— 新增条目只会让后续页整体后移，不会出现漏条或重条；
- 「移动条目到另一个时间点」退化成一次字段更新，不必维护邻居指针。

这是整个一致性设计里最省事的一层：**把顺序当作查询结果而不是数据，就没有一致性问题。**

### 5.2 字段层：乐观锁 + 三方合并

**写入用 compare-and-swap，不是「先读后写」。**

每次写入携带客户端读到的 `version`，服务端执行条件更新：

```sql
UPDATE events SET ..., version = ? + 1
WHERE id = ? AND version = ?
```

命中 0 行即说明有人抢先写入 → 抛 `EditConflictException`。这是数据库层面原子的，
不依赖应用层锁，也不受进程数影响。

**冲突时不报错，而是做字段级三方比对。** 拿客户端声明的基线版本对应的 revision 快照作为 `base`，
与 `theirs`（当前值）和 `mine`（本次提交）逐字段比较：

| 情况 | 处理 |
| --- | --- |
| 只有对方改了 | 保留对方，记入 `theirsOnly`，**自动并入** |
| 只有我方改了 | 采用我方，记入 `mineOnly` |
| 双方都改、值相同 | 不算冲突（殊途同归） |
| 双方都改、值不同 | **字段级冲突**，交用户裁决 |
| 本次没提交该字段 | 对方改了就用对方的 |

关系字段（出处 / 人物 / 阵营 / 标签）也参与比对。初版只比标量属性，会出现
「两个人同时改了出处却没有任何提示」的静默覆盖，已修正为整份快照比对。

**基线不可用时的保守策略。** 若客户端声明的版本快照已被裁剪（拿不到 `base`），
不采用「以对方为基线」的乐观假设（那等于把客户端提交的内容一律当成己方改动、静默覆盖对方），
而是**把所有不一致都判为冲突**交给用户裁决。宁可多问一次，也不能悄悄丢掉别人已经确认过的内容。

**冲突裁决的回写**走 `/events/{id}/resolve-conflict`：客户端给出逐字段裁决（`mine` / `theirs` / 自定义值），
服务端以**最新版本**为基线拼装后重新 CAS 写入，因此不会二次冲突（除非这几秒内又有人写入，那会再返回一次 409 并刷新面板）。

**格式校验规则单点定义。** 创建与更新共用同一个 trait 的规则集，避免两处漂移 ——
校验规则漂移是协作系统里最隐蔽的 bug 来源。

### 5.3 软锁：为什么不做硬锁

编辑条目时会获取一个 **5 分钟的编辑租约**（`event_locks`，60 秒续租，到期自动回收）。

它是**软锁**：**不阻止他人编辑**，只把「谁正在编辑什么」公开出去，让冲突从「信息不对称导致的重复劳动」
变成「可预期的合并」。理由：

- 硬锁会产生僵尸锁（用户直接关标签页），把条目永久锁死，比偶尔的冲突严重得多；
- 真正的数据安全已经由乐观锁保证 —— 即使软锁被绕过，也不会丢更新。

租约被他人持有时，接口返回 409 + `locked_by_other`，前端提示但仍允许提交（会走冲突合并）。
审核员可以强制接管，保留人工兜底。

### 5.4 语义层：收敛式巡检

上面两层解决的都是「同一秒的写入竞争」。但绝大多数不一致其实是语义层的：
**A 把事件定在 1097 年，B 把它的起因定在 1099 年 —— 两个人都没写错格式，拼起来是错的。**
这类问题无法在写入瞬间判定，只能用规则持续收敛。

`TimelineConsistencyChecker` 的检查项：

| 类型 | 判据 | 级别 |
| --- | --- | --- |
| 因果倒置 | `event.start_index < caused_by.start_index` | 阻断 |
| 子早于父 | `event.start_index < parent.start_index` | 阻断 |
| 锚点失效 | 精度为 relative 且索引未解析 | 阻断 |
| 时代错位 | 条目索引落在所属纪元区间之外 | 警告 |
| 出处矛盾 | 出处引文中的年份与条目年份相差超过容差 | 警告 |
| 疑似重复 | 标题相似度 ≥ 阈值且时间区间重叠 | 警告 |
| 单日过载 | 同一时间点聚集条目数超阈值 | 提示 |

两个关键设计：

1. **写入后同步体检 + 定时全量巡检**。前者保证新问题立刻可见，后者保证历史数据与新增规则同样被覆盖。
2. **收敛而非累积**：`fingerprint` 唯一索引防重复告警；每轮体检后，
   本轮未复现的 `open` 异常自动置为 `resolved`。因此收件箱里剩下的每一条都代表**此刻仍然存在**的问题，
   不会变成没人看的噪音坟场。

阻断级异常会挂住「标记已校验」（`Event::hasBlockingAnomalies()`），
让「有问题但被标成已校验」在流程上不可能发生。

### 5.5 冲突处理决策树

```
用户点保存
  │
  ├─ 权限 / 状态 / 出处范围不允许 ──────────► 403 + 具体原因（不是笼统的「无权限」）
  │
  ├─ version 匹配 ─────────────────────────► 写入成功，生成新 revision
  │
  └─ version 落后 ─► 409 + 字段级 diff
        │
        ├─ 无字段冲突 ───────────────────► 「双方改动互不重叠」→ 一键合并
        └─ 有字段冲突 ───────────────────► 合并面板：逐字段裁决 → 以最新版本重写
```

### 5.6 失败模式与对策

| 失败模式 | 对策 |
| --- | --- |
| 两人同时编辑同一条目 | 乐观锁 CAS；后者不覆盖，进入合并流程 |
| 两人改到同一个字段 | 字段级三方 diff，人工裁决，两侧输入都不丢 |
| 两人改不同字段 | 自动合并，无需人工介入 |
| 用户关掉页面留下「正在编辑」 | 租约自动过期回收；且不影响他人写入 |
| 有人录入了错误的时间 | 版本链可回滚（回滚生成新版本，历史不覆盖） |
| 两条冲突规则在群里吵不出结果 | 条目置为 `disputed` 冻结正文，annotation 集中讨论，reviewer 裁定 |
| AI 产出了看似合理的假事件 | 提案制 + 四层校验 + 硬闸门 + 审核留痕 |
| 重新解析规则后发现历史数据不符 | 定时全量巡检 + `--rebuild` 重算纪元归属 |
| 有人删错条目 | 软删除 + 版本链可恢复（需 reviewer） |

### 5.7 已知边界

诚实列出当前没有做的事，避免被误读为「已经解决」：

- **正文级内容冲突**不做自动合并。两个人都重写了 `details` 时只能人工裁决，不做文本 diff 合并。
- **没有实时协同编辑**（无 OT/CRDT）。多人同时编辑同一条目靠乐观锁 + 合并，而不是实时同步。
- **相对时间只解决了「解析与标记」**，锚点自动回填尚未实现：`precision = relative` 的条目会先进入「时间未定」泳道，并由巡检告警，等人工指定锚点。
- **一致性巡检是规则式的**，不是语义推理。它能发现「结果早于起因」，但发现不了「起因与结果其实无关」。
- **账号管理没有审计日志的导出与保留期策略**。日志只增不改且会一直留着，量级在几十人的团队里没问题，
  但没有归档或导出功能。
- **种子数据集是起始语料，不是权威年表**。其中大量条目在社区考据中属于推断而非官方明写 —— 这正是产品要解决的问题本身，条目上的 `date_confidence` 会如实标注。
  其中《大地巡旅》来源的条目分两种口径：散文卷（世界卷 / 国家与地区卷）**不附引文、不写年份**——
  原文尚未逐页录入，而编造引文会直接摧毁 L3「引用可定位」这条防幻觉主力；
  书末附录「泰拉纪年」则相反，它是官方年表原文，条目**必须**带年份与逐字引文。
  系统因此选择把「引文待补」作为**显式的待办状态**呈现（出处页会写「该出处尚未附引文」），而不是留白让人误以为已经核对过。

> （此时若数据库在宿主机上，需要 `DB_HOST=host.docker.internal`）。
